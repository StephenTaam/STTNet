Chapter 15: Encoding, Crypto, Randomness, and Data Conversion

Understand the real boundaries of Base64, SHA-1, AES-CBC, randomness, numeric conversion, and byte order.

1. Encoding is not encryption

EncodingUtil::base64_encode/decode changes representation only. It is useful for carrying binary bytes in text protocols and provides no secrecy.

2. Hashing and symmetric encryption

APIPurposeSecurity boundary
CryptoUtil::sha120-byte binary SHA-1Protocol compatibility, not passwords or new signatures
CryptoUtil::sha1140-character hex SHA-1Readable checksum, not a password hash
encryptSymmetric/decryptSymmetricAES-256-CBCCBC has no authentication; prefer TLS or an authenticated design
const std::string encoded = EncodingUtil::base64_encode("hello");

std::string digest;
// Hex SHA-1 for compatibility or ordinary checksums only.
CryptoUtil::sha11("hello", digest);
Do not use SHA-1 as a password hash. Use Argon2, scrypt, bcrypt, or PBKDF2 with a unique random salt. A fixed-IV AES-CBC example is not a complete secure storage format.

3. Randomness

RandomUtil is appropriate for test data, ordinary sampling, and protocol masks. Use OpenSSL RAND_bytes() or the operating-system CSPRNG for secrets, keys, IVs, and authentication tokens.

4. Conversion utilities

  • NumberStringConvertUtil does not throw and writes a caller-selected fallback on failure.
  • PrecisionUtil can either format to text or mutate a numeric value. Do not use binary floating point as the final representation of money.
  • NetworkOrderUtil::htonl_ntohl_64 swaps eight bytes of unsigned long on STTNet's 64-bit Linux target. New protocols should prefer fixed-width uint64_t.
  • HttpStringUtil is a low-level helper. Prefer the already parsed HttpRequestInformation in server callbacks.
